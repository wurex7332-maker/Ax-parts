## 1. 背景与目标

### 1.1 背景

车间辅料的档案、库存、预警、采购审批目前无统一系统承载。本平台为**测试性质**项目，不接入生产系统，目标是用模拟数据验证「档案 → 库存 → 预警 → 采购审批 → 看板」全链路在 Web 后台与手机 H5 两端是否可用、是否好用。后端服务由独立需求实现，前端从零搭建并通过 REST API 消费。

### 1.2 目标

| # | 目标 | 判定方式 |
| --- | --- | --- |
| G1 | 覆盖 Web 后台（桌面）与手机 H5 两类形态 | 路由与页面清单齐备，构建为单一静态站点 |
| G2 | 全链路可演示 | AC-1~AC-5 可在同一浏览器内点选复现 |
| G3 | 单一权威数据源 | 库存与审批状态全部来自 API 返回；写操作后重拉，不做本地累加 |
| G4 | 易用性：入库/出库 ≤3 步，扫码领用 ≤2 步 | AC-7 按 §6.4 口径计数 |
| G5 | 三态（正常/预警/断料）双端清晰可辨 | 颜色 + 文字 + 图标三重编码，AC-2 可测 |
| G6 | 产物为可访问静态站点 | AC-6：`serve dist` 直接打开，无需启动后端 |

### 1.3 非目标

不做原生 App / 小程序；不做二维码生成与赋码；不做报表导出打印；不做真实采购与支付对接；不做生产级鉴权；不修改后端分支代码。

## 2. 需求前提校验（三处必须先说清的问题）

本节不是挑刺，而是防止按错误前提开发。

### 2.1 「两级审批」与正文矛盾 —— 实际只有一级

需求 §5.4 标题为「采购管理（两级审批）」，但正文与 §3 角色表只定义**车间主管一次通过/驳回**。后端状态机同样只有一次审批动作（`PENDING --APPROVE--> APPROVED`）。**结论：不存在第二级审批。**「两级」应理解为「提出 → 审批」两个环节，或「审批 → 订单执行」两个阶段。若确需两级会签，后端须新增状态（如 `APPROVED_L1`），属需求变更，不在本方案内。

### 2.2 F4 表单字段与后端契约不一致

| 需求字段 | 后端实际 | 处置（已确认：以后端为准） |
| --- | --- | --- |
| 预算 | **无此字段**；`forbidNonWhitelisted` 下传了直接 400 | 前端只读估算：`单价 × 数量`，标注「估算金额，不入库」 |
| 供应商 | **无此字段**（后端按 SKU 关联档案） | 由 `GET /materials/{sku}` 带出只读展示 |
| 备注 | 后端为 `reason`（**必填**） | 合并为单一字段「申请理由 / 备注」，必填 |
| （需求未列） | `expectedDate` **必填** | 新增「期望到货日期」，默认 today+7。属契约强制，非功能扩展 |

另：需求写「驳回必须**可填**原因」，后端为 `REJECT_REASON_REQUIRED`（**必填**）。按必填实现。

### 2.3 状态机「已到货」不可观察

后端 `ARRIVE` 在单个事务内完成 `PURCHASING → ARRIVED → COMPLETED`，`ARRIVED` 从不落库，任何 GET 都读不到。处置：步骤条保留 5 个节点（满足展示要求），「已到货」标注为「瞬时态：到货即完成」；`COMPLETED` 时该节点显示为已达成。不伪造状态。

### 2.4 其他认知偏差

| 偏差 | 事实 |
| --- | --- |
| 「预警数」直觉上包含断料 | 后端 `dashboard.alertCount` **仅统计 LOW**，断料单列 `stockoutCount`。前端不相加，卡片副标题写明口径 |
| 「类别」可自由填写 | 后端仅允许 5 个中文枚举：计算机设备 / 计算机配件 / 打印设备 / 耗材 / 网络设备 |
| 「单位」可自由填写 | 后端仅允许 **4** 个：台 / 个 / 盒 / 箱 |
| 台账一行 = 一个物料 | `GET /stock` 是 **SKU × 库位** 粒度；行内 `currentStock` 是库位级，`health` 却按 SKU 合计（`skuCurrentStock`）判定 |
| AC-4 领用后看板数字会变 | MON-004 由 8→5，安全库存 3，仍 NORMAL：四张卡片数字**全部不变**。可见证据是台账行、流水、健康度分布三处（见 §6.6） |

## 3. 用户角色与核心场景

### 3.1 角色

| 角色 | 端 | 核心任务 | 视角边界 |
| --- | --- | --- | --- |
| 库管员 `warehouse` | Web | 档案维护、入库、出库、盘点、调整、查询 | F1–F3 + F5 + F4 申请/订单/到货 |
| 车间主管 `supervisor` | Web + 手机 | 采购申请通过/驳回、查看预警与看板 | 双端均有审批入口 |
| 采购员 `buyer` | Web | 建申请、跟单、到货入库 | F4 全流程 |
| 领用人员 `operator` | 手机 | 扫码领用、库存查询、站内消息 | 手机端**仅**领用/查询/消息 |

> 后端无鉴权（无 Guard / 无 JWT / 无 role 字段），身份仅靠请求头 `X-Actor` 写入 operator 字段，可任意伪造。角色是**前端视角收敛**，不是安全边界，UI 与 README 必须显式声明。

### 3.2 核心场景

| # | 场景 | 主线 |
| --- | --- | --- |
| S1 | 库管接采购到货 | 台账 → 「采购入库」（类型已预选）→ 选物料 → 填数量 → 提交 → 看到当前库存与三态 |
| S2 | 库管发现物料将用完 | 看板看到断料 → 预警列表（断料置顶）→ 行内「生成采购建议」→ 表单已预填 → 核对后提交 |
| S3 | 主管在车间手机上批单 | 消息提示待审批 → 审批列表 → 详情 → 驳回并填原因 → 状态回待审批，Web 端同步可见 |
| S4 | 领用人员领 3 台显示器 | 手机首页 → 扫码 → 带出 MON-004 / A-03 / 8 → 数量 3 → 确认 → 扣减后 5 |
| S5 | 采购员跟单 | 订单列表 → OPEN 订单 → 到货 → 库存增加、申请转完成、生成到货消息 |

## 5. 业务流程

### 5.1 F1 档案

```
列表(筛选/分页) → [新增] → 表单(11 字段) → 校验 → POST /materials → 回列表并高亮新行
                → [编辑] → PUT /materials/{sku}（不提交 sku，否则 400）
                → [停用] → 确认弹窗 → POST /materials/{sku}/disable → 行标记"已停用"
```

- 图片：本地选择 → 压缩至 ≤512px / ≤200KB → 预览 + 可填 alt → 提交 `imageUrl` 字符串。
- 校验：SKU 必填唯一（`DUPLICATE_SKU` 409 兜底）、数值非负、类别/单位取自枚举。
- 停用后：入库/出库/盘点/调整/新建申请均不可选（`MATERIAL_DISABLED` 409 兜底）。

### 5.2 F2 库存

| 操作 | 流程 | 步数 |
| --- | --- | --- |
| 入库 | 入口（类型已定）→ 选物料（自动带出名称/单位/库位）→ 填数量 → 提交 | 3 |
| 出库 | 入口 → 选物料 → 填数量（领用人默认带出）→ 提交 | 3 |
| 盘点 | 选库位 → 列出该库位物料及账面数 → 逐行录实盘数 → 实时显示盘盈/盘亏 → 确认（逐条串行过账） | — |
| 调整 | 选类型（报损/调拨）→ 选物料与数量 → 报损填库位；调拨填源/目标库位 → 提交 | — |
| 流水 | 列表（时间/类型/SKU/数量/操作人/关联单据），支持物料/类型/时间筛选 | — |

约束：出库可用量按 **SKU 合计**校验（非库位），`location` 只决定落账库位；盘点差额为 0 不产流水；`TRANSFER` 必须给源与目标库位；`LOSS` 必须给库位；流水 append-only，无编辑/删除入口。

### 5.3 F3 预警

```
GET /alerts（后端已只返 LOW/STOCKOUT，STOCKOUT 优先）
  → 断料区置顶 + 预警区，含 SKU/名称/当前/阈值/库位/供应商
  → 行内[生成采购建议] → 跳 /admin/purchase/requests/new?from=alert&sku=&qty=
  → 表单预填（见 §6.3）→ 核对 → 提交 → 进申请详情
```

判定口径（后端 `health.ts`，前端复用同一实现）：`当前 ≤ 0 → 断料`；`当前 ≤ 安全库存 → 预警`；否则正常。断料优先级恒高于预警（安全库存为 0 时，任何 0 库存都判断料）。

### 5.4 F4 采购

```
新建申请(PENDING) → 主管审批
                     ├─ 通过 → APPROVED → [生成采购订单] → PURCHASING
                     │                                      → [到货入库] → COMPLETED（瞬时经 ARRIVED）
                     └─ 驳回(原因必填) → 状态仍为 PENDING，写入 rejectReason
                                         → [重新提交] → 清空 rejectReason，仍 PENDING
一申请最多一单；乐观锁 version 每次迁移 +1
```

| 当前状态 | 可执行动作 | 执行角色 |
| --- | --- | --- |
| PENDING | 通过 / 驳回 / 重新提交 | supervisor / buyer（重提） |
| APPROVED | 生成采购订单 | buyer |
| PURCHASING | 到货入库 | buyer / warehouse |
| COMPLETED | — | — |

驳回不产生独立状态。前端在 PENDING 且 `rejectReason` 非空时显示「已驳回待重提」徽标 + 原因区块，与普通待审批区分。

### 5.5 F5 看板与报表

看板 4 卡口径（严格照后端字段）：`skuTotal`（SKU 总数）、`alertCount`（**仅预警**）、`stockoutCount`（断料）、`pendingPurchaseCount`（PENDING+APPROVED+PURCHASING）。健康度分布为 normal/low/stockout 三段，图旁必须有等价数据表。

报表 4 Tab：出入库流水、消耗排行（仅统计 `OUT_ISSUE`）、预警清单、采购统计（各状态计数 + 申请/订单/到货量 + 未关单数）。

### 5.6 F6 手机端

| 功能 | 流程 | 步数 |
| --- | --- | --- |
| 扫码领用 | 进页面自动开扫 → 命中即带出物料卡 → 数量默认 1 → 确认 | **2** |
| 库存查询 | 搜索（SKU/名称）→ 结果卡（当前库存/库位/三态） | — |
| 审批 | 待审批列表 → 详情 → 通过 / 驳回（全屏确认 + 原因） | — |
| 消息 | 列表（未读标识）→ 点击标记已读 → 直达对应处理页 | — |

手机端导航仅 4 项：领用、查询、审批、消息，**结构上不含任何 `/admin` 链接**。

## 6. 交互规则

### 6.1 三态编码（唯一出口 `HealthBadge`）

| 状态 | 色 | 图标形状 | 文字 | 附加冗余 |
| --- | --- | --- | --- | --- |
| 正常 NORMAL | 绿 | 实心圆 + 勾 | 正常 | — |
| 预警 LOW | 琥珀 | 三角 + 感叹号 | 预警 | 左侧描边 |
| 断料 STOCKOUT | 红 | 八角 + 叉 | 断料 | 加粗 + 左侧 3px 条纹 |

禁止仅用色块。徽标 `aria-label` 含数值与阈值（如「状态：断料（当前 0，安全库存 5，需立即补货）」）。列表排序与后端一致：断料优先。

### 6.2 通用交互约定

| 项 | 规则 |
| --- | --- |
| 金额 | 传输与存储一律**整数分**（`priceCents`）；界面显示元两位小数；`MoneyInput` 内部换算 |
| 数量 | 整数 `≥1`（盘点实盘数 `≥0`）；步进器按钮 ≥44px |
| 分页 | `page` 默认 1、`pageSize` 默认 20、上限 200；`/purchase/orders` 与 `/alerts/generate-suggestions` 无分页 |
| 高风险确认 | 驳回、报损、盘点提交、停用物料需二次确认；确认框默认聚焦「取消」 |
| 重复提交 | 提交中按钮 `disabled + aria-busy`；出库额外带 `Idempotency-Key` |
| 错误提示 | 一律按错误体 `code` 分支（**无 statusCode**）；表单类定位到字段并聚焦；状态类（`ILLEGAL_STATE_TRANSITION`）提示后强制重拉 |
| 成功反馈 | toast + `aria-live` 播报，含关键数值 |
| 数据刷新 | 写成功后按失效表重拉，不用返回体累加；返回体仅用于结果播报 |
| 角色切换 | 顶栏下拉，写入 `X-Actor` 与本地会话；文案标注「演示视角，后端不做鉴权」 |
| 停用物料 | 库存变动入口不可选；强行提交由 `MATERIAL_DISABLED` 拦回 |
| 时间 | 服务端 ISO8601，本地时区展示；日期筛选必须以 ISO 传参 |

### 6.3 预警一键预填

后端 `generate-suggestions` 只返回 `{sku,name,currentStock,safetyStock,level,suggestedQty}`，**无供应商**，故需额外调 `GET /materials/{sku}`：

| 字段 | 取值 |
| --- | --- |
| 物料/SKU/单位/库位 | 物料详情 |
| 供应商（只读） | `mat.supplier`，空则「—」 |
| 数量 | `suggestedQty`（后端公式 `max(2×安全库存 − 当前, 1)`） |
| 期望到货日期 | today + 7 天（可改） |
| 申请理由 | 断料：`断料补货：{名称}({SKU}) 当前 0，安全库存 {N}`；预警：`库存预警补货：…当前 {M}，安全库存 {N}` |
| source / applicant | `ALERT` / 当前用户显示名 |
| 估算金额（只读） | 数量 × 单价，标注「估算」 |

### 6.4 步数口径

按需求 §8.3：从入口点击到提交成功的主操作次数，系统反馈等待与自动带出不计数。

- 入库：选物料 ① → 填数量 ② → 提交 ③ = 3（类型由入口带入，切换不增主操作）
- 出库：选物料 ① → 填数量 ② → 提交 ③ = 3
- 扫码领用：扫码 ①（识别为系统行为）→ 确认提交 ② = 2。扫码不可用时手动输入等价计 1 次

### 6.5 权限与路由守卫

| 路由区 | 允许角色 | 越权表现 |
| --- | --- | --- |
| `/admin/*` | warehouse / supervisor / buyer | 渲染「当前视角无权访问」页（含切角色按钮），不重定向 |
| `/m/scan`、`/m/search` | operator / supervisor | 同上 |
| `/m/approvals*` | 仅 supervisor | 同上；operator 的底部 Tab 不出现审批 |

AC-10 双重保险：导航由 `mobileNav[]` 常量渲染（不含 `/admin`），守卫再做角色过滤；测试直接断言 `/m` 子树内 `a[href*="/admin"]` 为 null。

### 6.6 AC-4 验收话术（必须按此演示）

MON-004 由 8 → 5 后：`skuTotal`、`alertCount`、`stockoutCount`、`pendingPurchaseCount` **均不变**（5 > 安全库存 3，仍 NORMAL）。可见证据三处：① 台账该行库存 5 ② 流水新增一条 `OUT_ISSUE` 数量 3 ③ 健康度分布不变（正常 3 / 预警 2 / 断料 1）。手机领用成功页提供「查看 Web 看板」直接跳转佐证。

## 7. 非功能要求

### 7.1 可访问性（AC-8）

| 要求 | 落地方式 |
| --- | --- |
| 语义与标题 | 每页唯一 `h1`（`PageHeader` 唯一出口），区块用 h2/h3；路由切换后聚焦 h1 |
| 表单 | 控件 `<label htmlFor>` 关联；提示/错误经 `aria-describedby`；错误 `role="alert"` + `aria-invalid`；失败聚焦首个错误字段 |
| 键盘 | 全站仅键盘可完成「新增辅料 → 入库 → 扫码领用」；SkipLink；下拉支持 ↑↓/Enter/Esc；弹窗用原生 `<dialog>`（焦点陷阱 + Esc + 焦点还原） |
| 状态非纯色 | 三态三重编码；链接带下划线；必填 `*` + `aria-required`；未读用「● 未读」文字 |
| 播报 | 全局 `aria-live="polite"` 播报成功与库存变化；错误用 `role="alert"` |
| 图表 | `role="img"` + `aria-label` 摘要 + 「查看数据表」（`<details>` 内 `<table>` 带 caption/th scope） |
| 图片 | 必须有 `alt`；无图用 `role="img" aria-label="无图片"` 占位 |
| 触摸目标 | 移动端可点元素 ≥44×44px；底部导航 56px + `env(safe-area-inset-bottom)` |
| 对比度 | 三态用「浅底 + 深字 + 描边」，文字对比度 ≥ 4.5:1 |
| 动效 | 尊重 `prefers-reduced-motion` |

### 7.2 响应式（AC-9）

Web 以 ≥1024px 为主布局，表格 <900px 转卡片或横向滚动；H5 以 375px 为基线、兼容 320–430px，关键页面无横向溢出，主操作在拇指区，适配安全区；看板卡片桌面多列、手机单列。

### 7.3 易用性与工程

步数见 §6.4；高风险操作二次确认；文案全站统一。纯静态产物、无外链 CDN、可离线点开；首屏 JS ≤200KB（gzip），路由级懒加载，扫码库按需异步加载；浏览器基线 Chrome/Edge 最新两版 + Safari iOS 15+。

## 9. 边界条件

| 类别 | 条件 | 期望行为 |
| --- | --- | --- |
| 库存 | 当前 = 0 | 断料；出库被 `STOCK_INSUFFICIENT` 阻断 |
| 库存 | 可用 < 申请数量 | 阻止提交并给出可用量 |
| 库存 | 安全库存 = 0 | 任何 0 库存均判断料 |
| 数量 | 0 / 负 / 小数 | 前端拦截；后端 `@Min(1)` 兜底 400 |
| 分页 | `pageSize > 200` | 前端不发超限值 |
| 物料 | SKU 重复 | `DUPLICATE_SKU` 409 → SKU 字段错误 |
| 物料 | 已停用 | 库存类操作不可选；强行提交被 `MATERIAL_DISABLED` 阻断 |
| 采购 | 非法状态迁移 | `ILLEGAL_STATE_TRANSITION` → 提示「状态已变化」+ 重拉 |
| 采购 | 重复建单 | `DUPLICATE_ORDER` 409 |
| 采购 | 驳回原因空白 | 前端拦截 + `REJECT_REASON_REQUIRED` 兜底 |
| 采购 | 已完成申请 | 只读，无动作按钮 |
| 幂等 | 同 `Idempotency-Key` 重复提交 | 只产生一条流水 |
| 盘点 | 账实一致 | `movement: null`，展示「账实相符」 |
| 调拨 | 源库位 = 目标库位 | 阻止提交 |
| 时间 | 日期筛选非 ISO | 前端强制 ISO |
| 存储 | localStorage 超配额 / 隐私模式 | 降级内存态 + 顶部提示「数据不持久」 |
| 摄像头 | 非 HTTPS 或 localhost | 不请求权限，直接给手动输入主路径 |
| 摄像头 | 权限拒绝 / 无设备 | 差异化文案 + 手动输入 + 相册识别 |
| 二维码 | 内容非 SKU | 「未识别的二维码」，保留手动输入 |
| 网络 | 后端不可达 | 统一提示「无法连接后端」并说明代理要求，不白屏 |
